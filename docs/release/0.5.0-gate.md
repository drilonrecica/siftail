# 0.5.0 public dogfood gate

**Assembled:** 2026-11-25
**Scope:** SFT-050 through SFT-058, with SFT-127–SFT-129 and the hardening
phases H0–H3 (SFT-082–SFT-126)
**Release action:** None. No tag, image push, artifact publication, or
`latest` update. Tagging and publishing are the maintainer's decision
([`process.md`](process.md)).

This gate assembles the evidence for the maintainer's decision on the first
public dogfood release. Everything under [Verification in this
gate](#verification-in-this-gate) was run in this session on the tree named
there. Evidence carried over from an earlier task is cited as such and was not
rerun unless the text says so.

## Verdict and recommendation

**No unresolved data-loss, recovery, security, or unbounded-resource defect
is known.** The one release blocker found by SFT-057, the reachable Go
standard-library vulnerability GO-2026-6859, is fixed in this task by moving
the toolchain to go1.27.4. The release artifacts build reproducibly from the
candidate tree and pass the image contract, the container smoke, every schema
upgrade, backup, verify, restore, the Compose deployment smoke, and a quick
soak.

**The evidence is not complete for a stable `0.5.0`.** Five acceptance items
have no evidence, and each is an owner action that was skipped or has not
happened yet (see [Open evidence](#open-evidence)): the Coolify deployment has
never been run on a real instance, the production container was never measured
on a quiet host or at 10 million events, the release workflow has never run on
GitHub (so there is no native arm64 smoke, image scan, or attestation), and
the human screen-reader and on-device phone reviews were skipped.

**Recommendation: publish a release candidate, not the stable release.**

1. Commit this gate and push `master`. Complete the one-time settings in
   [`process.md`](process.md#maintainer-steps) (the protected `release`
   environment, private vulnerability reporting).
2. Run **Actions → Release → Run workflow** with `0.5.0-rc.1` as a dry run.
   This is the first run of the workflow and produces the missing arm64
   smoke, Trivy scan, and second-runner reproduction.
3. Tag `v0.5.0-rc.1`, approve it, and deploy that image on the maintainer's
   Coolify instance by following [`coolify.md`](../operations/coolify.md).
   Record the run in the guide's Validation record. That closes the Coolify
   item with the real artifact, which is what a dogfood candidate is for.
4. Run SFT-129 when the host is quiet, or accept the limitation in writing.
5. Tag `v0.5.0` when items 2–4 hold and the candidate has run without a new
   data-safety finding.

The alternatives are to tag `v0.5.0` now and accept the five open items as
documented limitations (they are all listed in
[`known-issues.md`](known-issues.md) and the release notes), or to tag nothing
until the owner tasks are done. The candidate route costs one extra tag and
gets the Coolify and workflow evidence from the real artifact instead of from
a workstation.

**Maintainer decision (2026-11-25):** the release-candidate route ("option 1,
release candidate first"). No stable `v0.5.0` tag until steps 2–4 hold. The
steps above are the maintainer's own actions; this gate performed none of
them.

### Upgrade and restore drill

For each checked-in fixture `internal/database/testdata/upgrades/schema-N.db`
(N = 1…10), copied to an owner-mapped directory on btrfs, the candidate
container ran `serve`, became ready, and answered the active `database check`
with `schema: 10/10`, `compatible: true`, `integrity: ok`. It stopped on
SIGTERM with exit 0, and the stopped `database check --full` reported
`integrity: ok`. On the upgraded schema-1 database, an online `backup`
reported `backup verified` (full, 159,744 bytes), `backup verify` agreed on
the SHA-256, and the stopped `restore --confirm RESTORE` reported `current
database: healthy`, `rollback: siftail.db.rollback`, `fresh login required:
true`; the server then became ready again. The fixtures are small synthetic
databases, so this proves correctness of the path in the shipped image, not
upgrade duration at size.

## Known limitations carried into the release

The full list is [`known-issues.md`](known-issues.md). The ones that matter
for the decision:

- **Online `siftail database check` fails on databases of about 1.6 GiB and
  more** (soak F1, medium): the CLI's 10-second control timeout. The stopped
  check works, and data is not affected. This is the only known issue that
  can mislead an operator during an incident.
- Readiness after a restart grows with database size: 174.5 s at 2.29 GiB
  (F2). A cleanup that meets a transient failure waits an hour (F4). Live
  closes unfiltered streams often under heavy load, by design (F3). Idle RSS
  after saturation was 71.6 MiB against the 50 MB idle target, flat (F5).
- The History and Live filter area is taller than designed on desktop (ADR
  0011 D1), with five smaller interface findings.
- Accessibility is a WCAG 2.2 AA target verified by automated checks in
  Chromium only.
- Several months of production use cannot be produced by a test and remain
  the `1.0.0` gate (SFT-059).
