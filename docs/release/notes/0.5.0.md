# Siftail 0.5.0: public dogfood release

**Status:** draft, pending the maintainer's release decision (SFT-058). Nothing
is published until the maintainer tags and approves it
([release process](../process.md)).

Siftail is a fast, private, self-hosted log viewer for Coolify and any Fluent
Bit HTTP source: one container, one Go process, one SQLite database, one
administrator, no telemetry. 0.5.0 is the first public release. It is meant for
dogfooding by people who are comfortable reading these notes and keeping
backups; `1.0` is reserved for proven operational stability (`PRODUCT.md`
§19.6).

## Added

- **Durable ingestion** at `POST /api/v1/ingest` for NDJSON and Fluent Bit
  `json_lines`/`json` payloads, authenticated by per-Server ingestion tokens.
  A request is accepted only after its SQLite commit, as a whole or not at
  all; a full queue answers `503` so Fluent Bit retries. Stable source event
  IDs deduplicate retries ([`coolify-fluent-bit-compatibility.md`](../../integrations/coolify-fluent-bit-compatibility.md)).
- **History**: filters by Server, source, container, level, stream, time
  range, literal `contains`/`excludes` text, and exact common fields, with cursor pagination, shareable URLs, inline detail,
  surrounding events, and a bounded text or NDJSON export.
- **Live tail** over Server-Sent Events, separate from History, with pause,
  bounded buffers, and an explicit truncation notice instead of blocking.
- **Servers, tokens, and sources in the browser**: one-time token display,
  rotation, aliases, source lifecycle, generated Coolify and Fluent Bit
  configuration, and a guided test ingestion.
- **Retention** by age and database footprint, set on Settings; disk-full
  degraded mode that keeps reads and sign-in working and recovers by itself.
- **Backup, verify, and restore**: full and configuration-only snapshots taken
  while ingestion continues, verification, and a stopped-server restore that
  keeps the previous database as a rollback.
- **Operations**: `/health/live`, `/health/ready`, a Status page, bounded
  sanitized diagnostics, online and offline database checks, and a security
  audit log.
- **Deployment**: the multi-architecture image (`linux/amd64`,
  `linux/arm64`), a supported Docker Compose deployment, and a manual Coolify
  guide ([operator guide](../../operations/operator-guide.md)).
- **Release automation**: reproducible builds, provenance and SBOM
  attestations, checksums, and the `edge`/candidate/stable channels
  ([release process](../process.md)).

## Changed

Since the 0.4.0 milestone builds, which were never published, a full audit
(`docs/audit/2026-11-04-full-audit.md`) was remediated in SFT-082 to SFT-126:

- Writes from concurrent requests share one commit (group commit, ADR 0009):
  about 8,000–9,600 events/s with 100-event batches on the reference host.
- Retention deletes by **receipt time**, so an accepted event is kept for at
  least the configured age (ADR 0008).
- Backups use `VACUUM INTO` snapshots; restore can replace a missing or
  unhealthy database with an explicit flag and never deletes it (ADR 0009).
- Container identity no longer collides when a container name or ID is reused
  (ADR 0006); retries of batches without timestamps are idempotent (ADR 0007).
- The operator-console interface: keyboard layer, a fixed 24-hour time display
  with the zone always stated, the shared filter model, no-JavaScript
  fallbacks, content-hashed cacheable assets, and a full light theme (ADR 0005,
  ADR 0011).
- CLI commands that change an offline database take the maintenance lock and
  refuse to run beside a live server.

## Fixed

The audit remediation fixed, among others: writer cache entries surviving a
source removal; health reporting ready while ingestion was failing; History
filters on request ID reading unbounded rows; requests without deadlines
holding readers; retention stalling the writer; and the container smoke test,
which had not been updated for the mandatory public URL. The task records in
[`docs/tasks/0.5.0-hardening.md`](../../tasks/0.5.0-hardening.md) list every
change with its evidence.

## Security

- Sign-in runs behind bounded admission (at most two concurrent Argon2id
  hashes, per-client lanes, an immediate `429` on overflow) and never locks out
  a recently successful client. Unauthenticated failures are audited as
  per-window aggregates in reserved capacity (ADR 0010).
- `SIFTAIL_PUBLIC_URL` is now the only source of origin checks, cookie
  security, and HSTS. On `https` the session cookie is `__Host-siftail_session`.
- Sessions end after 12 hours idle and 7 days absolute; "Sign out other
  sessions" is available.
- The browser backup directory is restricted, the generated Fluent Bit input
  binds to loopback, and return paths, forwarded addresses, names, and the
  control socket are validated more strictly.
- The image runs as `65532:65532` with no shell or package manager, and every
  build is scanned for fixable HIGH/CRITICAL vulnerabilities and secrets.

Review and residual limitations:
[`0.5.0-hardening-review.md`](../../security/0.5.0-hardening-review.md).
Reporting: [`SECURITY.md`](../../../SECURITY.md). Siftail still has no telemetry
and makes no outbound request in ordinary operation.

## Database migrations

Schema version **10**. Startup applies every missing migration forward and
transactionally; a binary refuses a database newer than it supports and
changes nothing. Migrations 5–10 are new since the 0.4.0 milestone builds:

| Schema | Change | Upgrade cost |
|---|---|---|
| 5 | Container identity without unique name/ID (ADR 0006) | Reads every event once for the foreign-key check: about 0.3 s per 2 million events on the reference SSD |
| 6 | `event_at_defaulted` flag for events without a timestamp | Column add |
| 7 | Retention index by receipt time (ADR 0008) | Builds one index over all events |
| 8 | Request-ID index in History order | Rebuilds one partial index |
| 9 | Security-audit row counter | Small table and triggers |
| 10 | Reserved unauthenticated audit capacity | Small table, triggers, partial index |

Every schema from 1 to 10 has a checked-in fixture that upgrades in CI
([`upgrade-compatibility.md`](../../operations/upgrade-compatibility.md)).

## Configuration changes

- `SIFTAIL_PUBLIC_URL` is **required** for `serve`, and must be an exact
  origin (no path, query, or fragment). `SIFTAIL_INGEST_PUBLIC_URL` must end
  in `/api/v1/ingest`. Both are already required by the Compose files.
- An unknown `SIFTAIL_*` variable stops startup and names it.
- The `_FILE` secret mechanism exists, but 0.5.0 has no secret setting, so any
  `SIFTAIL_*_FILE` variable stops startup.
- Retention limits are set on Settings, not in the environment.

Full reference: [operator guide §2](../../operations/operator-guide.md#2-configure).

## Compatibility

- Image: `ghcr.io/drilonrecica/siftail:0.5.0` for `linux/amd64` and
  `linux/arm64`. Linux containers only.
- Public contracts (`ARCHITECTURE.md` §31): the ingestion HTTP contract, health
  endpoints, documented CLI commands, environment variables, database upgrade
  behavior, backup compatibility, and the export format versions. HTML
  fragments, templates, and the database schema are not public interfaces.
- Backups restore into the same or a newer Siftail, which migrates them
  forward; an older binary refuses a backup with a newer schema.
- Before 1.0 only the latest stable release is supported.

## Upgrade instructions

From a 0.4.0 milestone build (fresh installs follow the
[operator guide](../../operations/operator-guide.md#1-install)):

1. Create and verify a backup and copy it off the volume
   ([operator guide §8](../../operations/operator-guide.md#8-backup-verify-and-restore)).
2. Set `SIFTAIL_PUBLIC_URL` and `SIFTAIL_INGEST_PUBLIC_URL` if they are not
   already set, then validate with the new image:
   `COMPOSE_SIFTAIL_IMAGE=ghcr.io/drilonrecica/siftail:0.5.0 docker compose run --rm siftail config validate`.
3. `docker compose pull siftail && docker compose up -d --wait --force-recreate siftail`.
4. Confirm `/health/ready`, then Status: version `0.5.0`, schema 10, no new
   diagnostics.
5. Sign in again: on `https`, the session cookie name changed.

Details: [Upgrading to 0.5.0](../../operations/docker-compose.md#upgrading-to-050-public-url-and-sessions).

## Rollback

0.5.0 advances the schema, so a 0.4.0 build refuses the upgraded database.
To roll back, stop Siftail, select the previous image, and restore the
verified pre-upgrade backup with `--replace-unhealthy`; the upgraded database
is kept unmodified in `siftail.db.unhealthy-*`. There is no down-migration
([operator guide §9](../../operations/operator-guide.md#9-upgrade-and-rollback)).

## Resource measurements

One-host observations, not guarantees
([`capacity.md`](../../operations/capacity.md) labels every figure):

- Image: about 38 MB unpacked on amd64 and 48 MB on arm64; binary about 13 MB.
- A fresh amd64 container became ready in under half a second and idled at
  about 15 MiB RSS.
- Write path: about 8,000–9,600 events/s with 100-event batches and 16
  producers, p95 commit about 190–250 ms (Go benchmark on a SATA SSD).
- Three-hour soak at 1,000–5,000 events/s with restarts, backups, a
  degraded-storage window, and retention: no acknowledged batch lost,
  duplicated, reordered, or partially stored; peak RSS 155.9 MiB; WAL at most
  217 MiB ([`0.5.0-soak.md`](../../performance/0.5.0-soak.md)).
- Not yet measured: the production container on a quiet host at sustained
  1,000 events/s and with 1–10 million stored events, and native arm64
  performance.

## Known issues

See [`known-issues.md`](../known-issues.md). The ones operators meet first:

- The online `siftail database check` reports a false failure on databases
  of about 1.6 GiB and more; run it with the server stopped.
- Readiness after a restart grows with database size (minutes at 2 GiB).
- The History and Live filter area is taller than designed on desktop.
