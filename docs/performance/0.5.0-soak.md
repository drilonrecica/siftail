# 0.5.0 bounded production soak

**Task:** SFT-055 (`docs/tasks/0.5.0.md`)
**Authoritative references:** `ARCHITECTURE.md` §§32–33, 36; `PRODUCT.md`
§19.5; `AGENTS.md` §§17, 29
**Harness:** `tests/containerbench/soak*.go`, run by `scripts/soak.sh` or
`make soak`

The soak runs the production container image for a fixed time under a mixed
workload, runs operational scenarios on a schedule, and then checks the final
database against the harness's record of every batch it sent. It drives only
public interfaces: the image's CLI (`podman exec` while running, `podman run`
when stopped), the ingestion endpoint, and the signed-in browser routes. One
exception: the degraded-database scenario also holds a SQLite lock from a
second process. The procedure is below. The results of the pre-public run
follow it.

## Procedure

### Running it

```bash
# Pre-public soak: three hours, about 15 GB free on a real disk.
make soak IMAGE=localhost/siftail:dev
# or
TMPDIR=/path/on/real/disk scripts/soak.sh <image> [--duration 3h] [--keep]

# Harness check only: 12 minutes, three short cycles.
scripts/soak.sh <image> --quick
```

`scripts/soak.sh` refuses a tmpfs, ramfs, or overlay `TMPDIR` (`AGENTS.md`
§17.2). It prints the kernel, CPU, load average, podman version, image ID and
architecture, filesystem, and device class. It builds the harness, runs it,
and writes one JSON summary (`$TMPDIR/soak.json` unless `OUT` is set). The
script exits non-zero if any gate below fails.

The container runs rootless under podman with no memory or CPU limits. The UI
is on `127.0.0.1:28280` and ingestion on `127.0.0.1:28281`. The data directory
is a bind mount on the real disk, owned by the image's `65532` user.

### Configuration

- Image defaults, except that `SIFTAIL_PUBLIC_URL` and
  `SIFTAIL_INGEST_PUBLIC_URL` are set to the loopback ports.
- Setup through the CLI: one administrator, three Servers (`edge-1`,
  `edge-2`, `edge-3`), one ingestion token each.
- Retention, set through the Settings form: 14 days and a 1 GiB size limit.
  A three-hour run writes several GiB, so size-triggered cleanup deletes
  data for real. It runs hourly and at every startup.

### Workload

- **Events.** The `ARCHITECTURE.md` §33.1 fixture of SFT-054
  (`tests/containerbench/fixture.go`). It has 12 sources on three Servers,
  weighted from 1.5% to 24% of events. It mixes plain text, JSON with request
  IDs, repeated health-check lines, stack traces, and messages from 60 bytes
  to about 1 KB, at several levels. Events carry the Coolify/Fluent Bit record
  shape with the time of sending. Every 50th batch has 100 events with one
  timestamp. Every event has the stable source event ID `soak-<n>`, so the
  database can be joined back to the batch that sent it. Content is a pure
  function of `n` and the workload seed (55), so a replay is byte-identical.
  There is no real application data and no external telemetry.
- **Ingestion.** Batches of 100 events, one Server per batch, 32 concurrent
  senders. The rate is 300 events/s, 1,000 events/s for five minutes, and
  5,000 events/s for 30 seconds of every cycle. Rejected or failed requests
  are retried with backoff from 250 ms to 4 s and no limit, as Fluent Bit's
  retry would. Input waiting behind blocked senders is capped at 60 seconds,
  like Fluent Bit's bounded buffer.
- **Readers.** One administrator session is shared by every tab, as browser
  tabs share a cookie. Four History readers each read a page every second,
  rotating through: unfiltered, one service, errors, a partial hierarchy, and
  a substring search over the last hour. Four Live streams are reconnected
  every two minutes. One slow Live client per cycle opens a stream and reads
  nothing for ten minutes.

### Schedule

Each 30-minute cycle runs, at these minutes:

| Minute | Scenario | Gate |
| --- | --- | --- |
| 0 | slow Live client opens (held for 10 minutes) | it connects; recorded whether Siftail closed it |
| 4 | checkpoint: RSS, threads, open descriptors | growth gate below |
| 5–10 | 1,000 events/s sustained | every batch acknowledged |
| 11 | 5,000 events/s for 30 s | every batch acknowledged |
| 13 | 20 acknowledged batches replayed byte-identically; 1 replayed with different content | all `204`; Status "Conflicting duplicates dropped" rises by exactly 100 |
| 14 | token rotation on one Server (`token create`, switch, `token revoke` while requests are in flight) | revoked token answers `401`, new token `204`, in-flight batches retried with the new token |
| 16 | session change: `sessions revoke-all` on even cycles, sign-out of a second session on odd cycles | revoked cookies answer `303`; the other session keeps working; tabs sign in again |
| 18 | source transition: every container name changes (a redeploy), and a new `release-<n>` service appears | batch acknowledged; new source and container instances recorded |
| 20 | online full backup and `backup verify` under ingestion | both succeed |
| 23 | graceful restart (cycles 0, 3): `podman stop --time 30` under load, then start | stops within 30 s; ready again; no acknowledged batch lost |
| 23 | queue saturation (cycles 1, 4): 64 senders × 1,000-event requests for 30 s, no retry | bounded rejection, at least one batch rejected; ready again within 2 min |
| 23 | degraded database (cycles 2, 5): an external process holds SQLite's write lock for 60 s | `/health/ready` turns `503`; ready again within 30 s of release; retried batches committed |

The sampler records the host's `/proc` view of the Siftail process every
15 seconds: RSS, high-water mark, threads, and CPU time. Every minute it also
records open descriptors, database, WAL, and shared-memory sizes, and the
Status page's queued-events and rejected-batches counts. The ingester records
the outcome and commit latency of every request, per minute.

### Final checks

After the last cycle the load stops and outstanding retries finish. Then:

1. Idle RSS over 60 seconds, plus a last checkpoint.
2. **Live capacity:** 17 concurrent streams. Exactly 16 must open. A
   subscription leaked by a reconnect, slow client, restart, or revocation
   would hold a slot.
3. **Critical queries** on the live server: newest page; a 26-page cursor
   walk with no duplicate; one service, errors, and substring filters; an
   exact request ID that returns exactly one event; event detail; and an
   NDJSON export of the last three minutes.
4. Online `database check`, Status snapshot, and a final online backup with
   `backup verify`.
5. Graceful stop, then `database check --full` on the stopped database.
6. **Offline verification** of a copy of the final backup against the
   harness's record. It runs `integrity_check` and `foreign_key_check`. For
   each batch it checks:
   - Every acknowledged batch is stored completely, unless size retention
     explains its absence. Retention deletes in `received_at_us` order, and
     Siftail stamps that time after the request starts. So an acknowledged
     batch whose last attempt started after the oldest stored
     `received_at_us` must be present. Anything else is a lost batch.
   - No `soak-<n>` ID is stored twice, and none was never sent.
   - No batch is stored partially, outside the retention cutoff.
   - Events of a batch are stored in send order.
   - No request rejected without retry is stored.
   - No conflicting replay content is stored.
   - The only non-soak events are the token-rotation probes, and every probe
     sent after the retention cutoff is stored.
7. **Restore drill:** restore the backup into an empty volume with
   `restore --confirm RESTORE --replace-unhealthy`, run `database check
   --full`, start a second container on it, sign in (backups exclude
   sessions), and read History.
8. **Cleanup:** remove both containers and every data, backup, and
   verification directory, unless `--keep` is given.

The race and stress suites (`make race-test`) run separately, after the soak.

### Gates

A run fails, and blocks completion, on any of the following:

- a lost, duplicated, phantom, partial, or reordered batch;
- a stored rejected batch or stored conflicting content;
- integrity or foreign-key errors;
- failed backups, checks, or the restore;
- a scenario failure from the table above;
- a Live capacity below 16;
- growth within one process lifetime, from the first to the last base-rate
  checkpoint, above 25 MiB RSS (the normal-memory regression threshold of
  `ARCHITECTURE.md` §33.4), 8 threads, or 16 descriptors;
- any History read error or Live connection failure outside a disruption
  window (restart, saturation, degraded, plus one minute);
- a History read over 10 s outside a disruption window;
- a Live connection that receives no frame under load;
- in a full run, size retention never deleting an acknowledged batch.

### Limits of the method

- Goroutines are not counted directly: the production image has no runtime
  endpoint. Threads, descriptors, RSS per process lifetime, and the Live
  capacity check stand in for that count. Goroutine-level leak checks are
  the race and stress suites.
- The degraded condition is `SQLITE_BUSY` from a held write lock, not a
  full disk. It runs the same degrade, probe, and recover path. The
  `SQLITE_FULL` path is covered by the repository's `max_page_count` quota
  tests (`docs/operations/storage-full-recovery.md`).
- The harness is the only client. Fluent Bit's own buffering and retry are
  modelled, not run.
- Numbers describe one host and one run. They are not guarantees for other
  hardware.

## Results: pre-public run, 2026-11-25

**Verdict:** every data-safety gate passed. No acknowledged batch was lost,
duplicated, reordered, or stored partially. Integrity and foreign-key checks
are clean, and backups, the restore drill, and the stopped-server full check
all succeeded. Memory, threads, and descriptors stayed flat within each
process lifetime. Every scenario passed in all six cycles. The run exited
`1` on two gates:

- the online `siftail database check` failed (finding F1 below, a real
  operator-tool defect);
- the probe-event check expected all six token-rotation probes to be stored.
  That expectation was a harness error: size retention correctly deleted
  the three probes received before its cutoff. The gate now accounts for
  retention, and this run's data meets the corrected rule (probes at 857,
  2,646, and 4,489 s were before the cutoff at 5,735 s; the three later
  ones are the three stored non-soak events).

The machine-readable summary of this run is
[`0.5.0-soak.json`](0.5.0-soak.json). It holds the environment, plan,
timeline, checkpoints, samples, per-minute ingestion, readers, Live,
verification, and failures, and no database or payload. A `--quick` run of
the final harness then passed every gate (exit `0`).

### Findings

None of these lost, corrupted, or misacknowledged data, and none is a leak.
They are recorded for the owner; the task does not change product code.

- **F1 — The online `database check` fails on large databases.** The CLI
  talks to a running server through the control socket with a fixed
  10-second client timeout (`controlRequest`, `cmd/siftail/admin.go`). The
  active `quick_check` takes longer than that on a 1.6 GiB database. The CLI
  then reports `active database check failed`, and the server records the
  cancelled check as "Failed · canceled". This happened at the end of the
  full run (load about 5) and in the first `--quick` attempt (235 MB, load
  18). The same timeout applies to each `backup` status poll: in that first
  quick attempt, `siftail backup` failed once with `backup status request
  failed` while the backup was running. The data was unaffected, and the
  stopped-server check worked. But `docs/operations/storage-full-recovery.md`
  tells operators to run this command during an incident, and a false
  failure is misleading there. Proposed follow-up: let control operations
  that are proportional to database size run without the 10-second client
  deadline (or poll them like backups), and give each status poll a
  deadline that survives a briefly stalled process.
- **F2 — Readiness after a restart grows with database size.** Startup
  runs `quick_check` before readiness. At 2.29 GiB on this host, the server
  was ready 174.5 s after start; with about 0.5 GB it took 4.6 s.
  Ingestion is refused meanwhile, and the clients retried
  (1,620 transport errors in total). This is the documented design, but
  `docs/operations/capacity.md` should give operators the figure.
- **F3 — Live truncation is frequent under this load.** 2,626 of 3,690
  unfiltered Live connections were closed by the server: the bounded
  publication path at 1,000–5,000 events/s, plus restarts. This is the
  `ARCHITECTURE.md` §17.2 behavior (truncate and close, never block), and
  reconnects worked every time. Narrow filters or a lower rate make it rare.
- **F4 — A cleanup run that meets a transient failure waits a full
  hour.** The hourly retention run due at minute 83 (one hour after the
  restart at minute 23) fell inside the 60-second degraded-lock window. The
  sampler does not record each cleanup's outcome, because Status shows only
  the last one. But the file, which incremental vacuum shrinks after a
  deletion, did not shrink then. It grew from 1.72 to 2.29 GiB against the
  1 GiB limit, until the restart at minute 117 ran cleanup at startup. The worker retries only at
  the next interval (`internal/retention/worker.go`). Proposed follow-up:
  retry sooner after a failed run while the footprint is above the limit.
- **F5 — Idle RSS after the soak is above the 50 MB idle target.** It was
  71.6 MiB after a 155.9 MiB saturation high water, with a 1.7 GB database.
  It is flat within each lifetime, so not a leak. The idle target applies
  to a quiet process. The quiet-host container measurement (the skipped
  SFT-129) is where that number belongs.

### Limitations of this run

- The host was shared and loaded, so latency figures are not baselines.
- One run of three hours. Variance between soak runs was not measured;
  three `--quick` runs of the harness were made while it was being
  developed.
- The degraded condition was `SQLITE_BUSY`, not `ENOSPC` (see the limits of
  the method above).
- Goroutines were not counted directly.
