# 0.4.0 recovery and security hardening review

**Reviewed:** 2026-07-28
**Scope:** SFT-048 combined backup, restore, audit, diagnostics, History
export, retention, ingestion, database recovery, and shutdown behavior
**Release action:** No tag, image, artifact publication, or public-release
claim

This review tests the system as one bounded appliance rather than treating
each maintenance feature as an isolated happy path. The applicable security
boundary is the Siftail process and its owner-controlled data directory.
An actor able to replace arbitrary files inside the mounted data directory or
alter the running process already controls the local database; Siftail does not
claim protection from a hostile host, root, storage administrator, or offline
database editor.

## One-writer and consistency review

The active process has one SQLite writer connection. Ingestion batches, audit
records, settings and source mutations, session cleanup, retention deletion,
and the storage-recovery probe all enter the database coordinator. Passive or
truncating checkpoints and incremental vacuum use the same coordinator's
maintenance operation, so they cannot overlap a writer transaction.

Online full backup deliberately does not enter the writer coordinator: it uses
SQLite's supported online-backup snapshot through a separate bounded reader
while ordinary commits continue. A concurrent commit is wholly before or
after SQLite's snapshot boundary. Configuration backup holds one source read
transaction while it counts and streams explicit rows. Backup finalization
changes only the staged artifact and records success through the coordinator
after final verification.

History export is read-only and holds at most one SQLite row plus one encoded
row in application memory. It can run with ingestion and retention; SQLite
snapshot semantics produce a consistent query result, while the hard row,
byte, and time limits bound the read. Audit recording is a separate mandatory
coordinated commit before any attachment headers.

Restore is excluded from the live process rather than serialized inside it.
`siftail serve` and `siftail restore` contend on the same advisory maintenance
lock. Restore stages and verifies both the input and the pre-restore rollback,
then either validates the installed database completely or automatically
reinstalls and validates the preceding state.

## Manual security checklist

- [x] No reviewed process-log call includes an incoming body, message, raw
  payload, attributes, authorization header, token, password, hash, full
  environment, or raw SQLite error.
- [x] Audit and diagnostic stores accept only closed, bounded metadata; export
  filters, filenames, paths, and event content are excluded.
- [x] Every browser state change reviewed remains authenticated, same-origin,
  CSRF-protected, body-limited, panic-recovered, and covered by strict security
  headers.
- [x] History export remains an explicit administrator POST and not a public
  administration API; GET and unauthenticated requests cannot generate data.
- [x] Incoming log content remains escaped by `html/template`; download
  formats frame hostile control/HTML content as JSON or quoted text data.
- [x] Backup and export artifacts use fixed/safe names, private staging,
  no-overwrite publication or response behavior, and `nosniff` where served.
- [x] Restore is CLI-only, requires exact `RESTORE`, excludes active sessions,
  preserves one verified rollback, and cannot run beside the server.
- [x] No telemetry, analytics, CDN, external asset, update check, or automatic
  ordinary-operation outbound API call was introduced.
- [x] Queue, decoder, live, audit, diagnostic, retention, backup, export, and
  database-coordinator capacities remain finite and independently enforced.
- [x] Failure responses and recovery instructions avoid credentials, payloads,
  host paths, hashes, SQL, and stack traces.

## Recovery guidance

- Corrupt or incompatible active database: stop and preserve the data
  directory. Use `siftail database check --full` and a verified supported
  backup; Siftail does not recreate the database.
- Storage-full degradation: free space or allow bounded retention to reclaim
  it. Ingestion resumes only after the internal net-zero transaction commits;
  restart or warning dismissal alone is insufficient.
- Interrupted restore: preserve `/data/restore-staging` and follow
  `docs/operations/restores.md`. Startup intentionally refuses it.
- Interrupted export: ordinary private staging is removed on the next startup.
  An unsafe matching entry stops startup; inspect ownership/type/permissions
  instead of deleting broadly.
- Managed rollback: copy `/data/siftail.db.rollback` to a separate private
  filename, verify the copy, and restore that copy through the normal command.

## Verification record

The review ran on linux/amd64 with Go 1.26.5, Node.js 22.22.2, and npm 10.9.7:

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race -count=1 ./...
make frontend-check
make playwright
go run golang.org/x/vuln/cmd/govulncheck@v1.6.0 -show verbose ./...
npm audit --omit=optional
git diff --check
```

All commands passed. The race run executed every Go package uncached. The
Chromium suite discovered and passed all 19 scenarios in about one minute,
including axe checks. `npm audit` reported zero vulnerabilities.
`govulncheck` reported no called-symbol or imported-package vulnerability. It
reported `GO-2026-5932` at module level because the required
`golang.org/x/crypto` module also contains the unmaintained `openpgp` package;
Siftail neither imports nor calls that package and uses the maintained Argon2id
implementation.

Focused fault coverage includes corrupt database preservation, migration
rollback, backup publication races and cancellation, restore faults after
installation, retention rollback/busy readers/storage recovery, ingestion
atomicity and queue saturation, export limits/cancellation/delivery
interruption, shutdown draining, unsafe filesystem entries, and
sensitive-marker rejection.

## Residual limitations

- Host/root/filesystem compromise can read or alter the database, backups,
  exports, rollback, and audit history. Use protected mounts, protected backup
  storage, and host/volume encryption when required.
- The advisory maintenance lock coordinates cooperating Siftail processes; it
  cannot stop an unrelated program from editing SQLite files.
- Audit history is bounded operational evidence, not an append-only forensic
  ledger. An offline database owner can alter or remove it.
- SQLite/host-filesystem durability is subject to storage honoring
  `fsync`/`FULL` synchronization guarantees.
- A client disconnect after ingestion queueing has an intentionally ambiguous
  outcome: the writer may still commit, so clients require at-least-once retry
  semantics and stable source event IDs where available.
- Export staging cleanup cannot prove whether a matching unsafe entry was
  created by Siftail or an external actor; fail-closed startup deliberately
  requires operator inspection.
- Browser automation covers Chromium and axe. Manual assistive-technology and
  cross-browser review remain release-gate evidence, not a claim of universal
  accessibility.
- `govulncheck` reports the module-only `GO-2026-5932` advisory for the
  unimported `golang.org/x/crypto/openpgp` package. There is no fixed module
  version because the package is deprecated; Siftail does not import it.
