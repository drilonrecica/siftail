# Siftail `0.5.0` hardening tasks

**Status:** In progress
**Release state:** Unreleased
**Task IDs:** SFT-082–SFT-128
**Milestone authority:** `PRODUCT.md` §19.5 (a public dogfood release must not
ship known data-loss, security, or accessibility defects)
**Source:** [`docs/audit/2026-11-04-full-audit.md`](../audit/2026-11-04-full-audit.md)

These tasks remediate the 2026-11-04 audit before the `0.5.0` public dogfood
gate. They are executed through the Igris plan in `tasks.md` (one fresh Claude
Code session per task, `make check` as the verify step, commits by igris). The
session implementing a task updates this file: status, `Issue/PR` (record
`direct maintainer implementation via igris`), completion date, and evidence
with actual commands and results. Igris owns the Status column in `tasks.md`;
this file remains the authoritative task record.

Phases: **H0** foundation for unattended runs → **H1** data integrity and
ingestion correctness → **H2** security and privacy → **H3** interface. Each
phase ends in a self-check gate that writes `docs/release/h<N>-gate.md` for the
maintainer's review after the unattended run. Audit finding IDs (DAT-, SEC-,
UX-) refer to the audit report.

Verification shorthand: *default verify* = `make check` (fmt-check, vet, test,
build, compose-check); *ui verify* = `make check && make playwright`.

### SFT-087 — Container identity migration (0005) and bounded pruning

**Status:** Done
**Milestone:** 0.5.0
**Depends on:** SFT-086
**Issue/PR:** — (direct maintainer implementation via igris)
**Completed:** 2026-11-05

**Authoritative references:** Audit DAT-01, DAT-14; ADR 0006; `DOMAIN.md`
§14; `AGENTS.md` §8, §18.

**Outcome:** A recreated or renamed container never blocks ingestion, and
`container_instances` stays bounded.

**Acceptance:**

- Migration `0005` rebuilds `container_instances` without
  `UNIQUE (source_id, container_id)` and `UNIQUE (source_id, container_name)`,
  keeps the FK and `UNIQUE (id, source_id)`, and is covered by an upgrade
  fixture under `internal/database/testdata/upgrades`.
- `resolveContainer` resolves by `(source_id, container_id)` and updates the
  name when it changes; events without a container id resolve by name only.
- A bounded cleanup removes container instances not seen within retention or
  beyond the per-server cap, oldest first, in chunks, under the coordinator.
- Regression tests: same name with a new id; same id with a new name; removal
  then re-ingestion of a container; pruning under the cap.

**Verification:** `make check`, `make race-test`, upgrade fixture tests, the
new regression tests.

**Impact:** Schema migration (forward-only; downgrade refusal documented in
`docs/operations/upgrade-compatibility.md`). Retention gains one more bounded
cleanup step.

**Completion evidence:** Added migration
`0005_container_identity.sql`, which rebuilds `container_instances` without
both producer-metadata UNIQUEs, keeps the source FK (with cascade), the column
checks, and `UNIQUE (id, source_id)`, copies rows with their IDs, and adds
`container_instances_source_container_id_idx` and the partial
`container_instances_source_name_idx`. SQLite rejects a referenced-parent
rebuild with `foreign_keys=ON` even under `defer_foreign_keys` (reproduced with
`sqlite3` 3.50.6: COMMIT fails), so `migrate.go` gained an opt-in first-line
directive `-- siftail:foreign-keys-off`: the migration runs on one pinned
connection with enforcement off outside its transaction, `PRAGMA
foreign_key_check` must be empty before commit, and enforcement is restored
and verified afterwards (the connection is discarded if that fails). Only 0005
uses it. `MaxSchemaVersion` is 5; the generator applies the same procedure and
produced `schema-5.db` (adds a recreated container with the same name and a new
ID); historical fixtures 1–4 and their digests are unchanged, and a second
generation into a scratch directory reproduced digest
`3e051e34…0870`. The writer resolves by `(source_id, container_id)`
(name-only events match only ID-less rows; most recently seen wins if a
defect ever stores duplicates), updates the label when a newer observation
renames the instance (a redelivered older chunk does not revert it), keys its
cache by ID or by name, verifies a cached instance in the transaction against
its full identity (SQLite reuses a freed max rowid, which the re-ingestion test
demonstrates), and counts the per-Server cap once per batch. The retention cycle
now prunes unreferenced instances in coordinator transactions of at most 1,000:
first those last seen before the age cutoff, oldest first, then per Server
above 90 % of its cap its oldest unreferenced instances by
`(last_seen_at_us, id)` down to 90 %. Interpretation recorded for the owner:
the writer never lets a Server exceed its cap, so DOMAIN §14's "while a server
exceeds its cap" is implemented as a 10 % headroom target; an instance with
retained events is never pruned. The cap moved to
`logs.MaxContainerInstancesPerServer`. New tests: migration preservation from
schema 4, FK restoration, dangling-reference refusal, directive parsing, index
usage, same name/new ID (including a mixed old/new batch), same ID/new name,
removal then re-ingestion with a stale cache and a reused rowid, name-only

(writer + cleaner end to end), and the prune probe using
`log_events_container_time_idx`. Updated schema-version expectations in
existing tests, `README.md`, the fixture README, and
`docs/operations/upgrade-compatibility.md` (schema 5, rebuild procedure,
downgrade refusal). Commands run: `make check` (exit 0), `make race-test`
(exit 0), `go test -count=3 -run 'Container|Reingests|NameOnly|ForeignKeys|Directive|Prun' ./internal/ingest ./internal/retention ./internal/database`
(ok), `go test -count=1 ./internal/database ./internal/backup` (ok),
`git diff --check` (clean). Measured the 0005 rebuild plus full
`foreign_key_check` on a 2,000,000-event, 515 MB schema-4 copy on btrfs on a
SATA SSD: 0.33 s total; a planted dangling reference was reported.

### SFT-088 — Writer cache invalidation after source removal

**Status:** Done
**Milestone:** 0.5.0
**Depends on:** SFT-087
**Issue/PR:** — (direct maintainer implementation via igris)
**Completed:** 2026-11-05

**Authoritative references:** Audit DAT-02; `DOMAIN.md` lifecycle sections;
`AGENTS.md` §9.

**Outcome:** Removing a source never poisons later ingestion.

**Acceptance:**

- Source and container cache hits are validated inside the write transaction
  (or the caches are invalidated by an epoch bumped by `RemoveSource` and
  `ClearLogs`); an FK failure caused by a stale cache entry is retried once
  with the entry cleared, within the same request.
- Test: remove a source while its key is cached, ingest again, expect 204 and
  a fresh source row; the same for a removed container instance.

**Verification:** `make check`, `make race-test`, the new tests.

**Impact:** No schema change. One extra indexed lookup per cached hit, or an
epoch read; measured in the completion evidence.

**Completion evidence:** Chose in-transaction verification (no epoch).
`persistTransaction` now confirms every source cache hit with one primary-key
lookup that also matches the full stable identity (`cachedSourceExists`),
because `sources.id` is a plain rowid and SQLite hands a freed max rowid to the
next new source; a miss falls through to normal resolution and re-caching.
Container hits were already verified the same way by SFT-087. `Persist` runs
the transaction through `persistAttempt`; a `database.IsForeignKeyViolation`
failure (new `CategoryError.ForeignKey`, set from
`SQLITE_CONSTRAINT_FOREIGNKEY`) clears the batch's source and container cache
entries (`boundedCache.Remove`) and retries exactly once in a new coordinator
transaction within the same request; caches are filled only after commit.
`ARCHITECTURE.md` §15.2 states both rules. New tests: writer-level
`TestBatchWriterReingestsAfterSourceRemovalWithReusedRowID` (RemoveSource on a
cached source, another source takes the freed rowid, re-ingestion creates a
fresh row and never attaches to the reused one),
`TestBatchWriterRetriesOnceAfterForeignKeyFailure` and
`TestBatchWriterForeignKeyRetryIsBounded` (an unexported `beforeInsert` test
seam deletes the resolved source inside the transaction to force the FK path:
two attempts, success; persistent failure stops after two, caches empty);
HTTP-level `TestIngestionAfterCachedSourceRemovalCreatesFreshSource` (204, one
source row without the removed alias) and
`TestIngestionAfterCachedContainerRemovalCreatesFreshInstance` (Clear logs plus
unreferenced-instance pruning, 204, fresh instance referenced by the event);
`database.TestClassifyMarksOnlyForeignKeyConstraints` (FK vs CHECK). Mutation
check: with source verification disabled the reused-rowid test fails
(misattribution that the FK retry cannot catch); with verification and retry
both disabled the HTTP source test returns 503 (the DAT-02 symptom) and the
retry test fails; restored afterwards. Impact, measured with `TMPDIR` on the
btrfs home disk: a temporary benchmark of the verification lookup alone gave
13.0–31.8 µs (median 14.1 µs), 993 B and 22 allocs per distinct cached source
per batch; `BenchmarkBatchWriterSQLiteCommit` (cached-hit path, count 10) went
from 7,065 B / 134 allocs to 8,067 B / 157 allocs per batch, with time
fsync-dominated (before 2.71–3.63 ms; after 3.03–5.68 ms plus one 128.9 ms
outlier), so the lookup is under 0.5 % of a commit. `make check` exit 0
(fmt-check, vet, test, build, compose-check); `make race-test` exit 0, no
races.

### SFT-089 — Ingestion error semantics and health truthfulness

**Status:** Done
**Milestone:** 0.5.0
**Depends on:** SFT-088
**Issue/PR:** — (direct maintainer implementation via igris)
**Completed:** 2026-11-05

**Authoritative references:** Audit DAT-03, DAT-08 (status code), DAT-12,
DAT-20, DAT-22; `ARCHITECTURE.md` ingestion and health sections; `AGENTS.md`
§9, §16.

**Outcome:** One bad batch affects only that batch; timeouts never look like
success; health reflects reality without inviting restart loops.

**Acceptance:**

- `CategoryConstraint` and `CategoryInternal` map to a batch-scoped response
  (4xx for client-caused constraint errors, 500 for internal) and never change
  the global database category; `Busy`, `IO`, and `Full` keep today's
  degradation semantics.
- A handler that reaches its request timeout writes 503 explicitly; it skips
  the write only when the client context is canceled.
- Authentication failures caused by database errors return 503, not 401.
- `ingestOutcomeWriter` writes the header once.
- `/health/ready` semantics on storage-full are documented in

### SFT-092 — Retention reclaim without stalling the writer

**Status:** Done
**Milestone:** 0.5.0
**Depends on:** SFT-091
**Issue/PR:** — (direct maintainer implementation via igris)
**Completed:** 2026-11-05

**Authoritative references:** Audit DAT-05, DAT-13; `ARCHITECTURE.md`
retention and maintenance sections; `AGENTS.md` §8, §14, §17.

**Outcome:** Retention runs in bounded, short writer holds and measures the
database footprint correctly.

**Acceptance:**

- Page reclaim uses `PRAGMA incremental_vacuum(N)` in chunks with coordinator
  yields between chunks; the maximum writer hold per chunk is documented and
  tested with a concurrent-ingestion test on a real-disk temp directory.
- Size retention computes the footprint as
  `(page_count − freelist_count) × page_size + wal size` and stops deleting
  once the target is met.
- `docs/performance/retention.md` is re-measured on real disk and states the
  filesystem.

**Verification:** `make check`, `make race-test`, retention benchmarks with
`TMPDIR` on the data volume.

**Impact:** Maintenance timing changes; no schema change.

**Completion evidence:** Reclamation in `internal/retention/cleaner.go` is now a
sequence of coordinator operations: a passive checkpoint, then
`PRAGMA incremental_vacuum(1024)` chunks (at most 8,192 pages per cycle,
stopping when the freelist is empty), then a truncate checkpoint. Each is its
own writer turn, so queued ingestion runs between them. The pragma frees one
page per result step. The old `Exec` would have stepped once, so the code
issued 8,192 `incremental_vacuum(1)` autocommit fsyncs in one writer hold. Now
each chunk drains its rows in one transaction and measures the pages it
released from the freelist delta. A zero-page request is rejected, because it
would release the whole freelist.

`ActiveFootprint(ctx, db, path)` measures
`(page_count − freelist_count) × page_size` in one statement over
`pragma_page_count()/pragma_freelist_count()/pragma_page_size()`, which is one
read snapshot, and adds the WAL and SHM file sizes. Size retention uses it by
default and keeps its stop-at-target loop. `CleanerOptions` gained
`VacuumChunkPages`, and `MeasureFootprint` now takes a context.

rewritten `docs/performance/retention.md` with the filesystem stated.

### SFT-098 — Group commit

**Status:** Done
**Milestone:** 0.5.0
**Depends on:** SFT-092, SFT-096
**Issue/PR:** — (direct maintainer implementation via igris)

**Authoritative references:** Audit performance observations; ADR 0009;
`ARCHITECTURE.md` §§8, 32; `AGENTS.md` §9, §17.

**Outcome:** Sustained throughput on real disks meets the 1,000 events/s
target without weakening `synchronous=FULL` or acknowledgement semantics.

**Acceptance:**

- The writer drains up to N queued batches into one transaction with a
  SAVEPOINT per batch; a failing batch rolls back to its savepoint and gets
  its own outcome; all acknowledgements wait for the single commit; Live
  publication happens after commit for every batch in the group.
- Bounds (N, bytes, max wait) are configurable with documented defaults and
  enforced by tests; the admission ledger accounting is unchanged.
- Benchmarks on a real-disk `TMPDIR` show before/after batches/s and p95
  commit latency; results recorded in `docs/performance`.

**Verification:** `make check`, `make race-test`, benchmarks, the
durability smoke test.

**Impact:** Core write path change; ADR 0009 and `ARCHITECTURE.md` updated.

**Completed:** 2026-11-05

**Completion evidence:**

- `internal/database/coordinator.go`: `Coordinator.DoImmediate` runs one
  `BEGIN IMMEDIATE` transaction on the coordinator turn, on a pinned writer
  connection with explicit `COMMIT`/`ROLLBACK`, because `database/sql` always
  begins with a deferred `BEGIN`. After a failure the connection is rolled
  back, or discarded if it is still in a transaction. `Statements` is the
  statement surface shared with `*sql.Tx`.
- `internal/ingest/writer.go`: `PersistGroup` persists N batches in one
  immediate transaction with a `SAVEPOINT` per batch. A batch-scoped failure
  (forbidden, constraint, internal) does `ROLLBACK TO` + `RELEASE` and becomes
  that batch's own outcome, while later batches continue. A transaction-level
  failure (busy, I/O, corrupt, full, any savepoint-statement failure, or a
  closed coordinator) fails every batch with the classified retryable outcome.
  The foreign-key retry is now a fresh savepoint inside the group. Caches fill
  only from successful batches after `COMMIT`. Live gets one call per
  successful batch in queue (ID) order. `Persist`/`PersistWithResult` are a
  group of one.
- `internal/ingest/worker.go`: the worker collects already-queued batches into
  a group under `GroupLimits` (max batches, max approximate retained bytes,
  max wait). A batch at or above the byte bound forms a group of one, and a
  batch that would overflow the group is carried to open the next one, so
  queue order holds. Each batch is observed and completed (acknowledgement and
  ledger release) only after the group returns. Shutdown drains through the
  same grouping. Admission-ledger accounting is unchanged.
- Configuration: `SIFTAIL_INGEST_GROUP_MAX_BATCHES` (64, 1–1024),
  `SIFTAIL_INGEST_GROUP_MAX_BYTES` (8 MiB, 1 to `SIFTAIL_QUEUE_MAX_BYTES`),
  and `SIFTAIL_INGEST_GROUP_MAX_WAIT` (0s, 0s–100ms), validated in
  `internal/config` and wired in `internal/app`. `retention.LoadAgeDaysTx`
  takes `database.Statements`.
- Tests: `internal/ingest/group_test.go` covers a failing batch with its own
  outcome while the others commit. A source created in a rolled-back
  savepoint is neither reused nor cached. Quotas and deduplication see earlier
  batches. Injected busy and real `SQLITE_FULL` fail every batch, then
  recover. The FK retry rolls back only its batch. Acknowledgement, Live, and
  ledger release wait for the single commit. The tests also cover the
  batch-count, byte, oversized-batch, and wait bounds, the shutdown drain, and
  limit validation. `internal/database/coordinator_immediate_test.go` checks
  savepoints, that the write lock is held before the first write, and that the
  writer is usable after a failure, including after SQLite's own rollback.
  `internal/config` tests cover defaults, overrides, and every out-of-range
  bound.
- Benchmarks with `TMPDIR` on btrfs on a SATA SSD
  (`BenchmarkGroupCommitConcurrent`, `-benchtime=1000x -count=3`; results and
  method in `docs/performance/group-commit.md`). At the defaults:
  - 1-event batches with 16 producers rose from 267–345 to 1,676–2,100
    batches/s, and p95 fell from 71–106 ms to 9–13 ms. Per-batch commit
    missed the 1,000 events/s target.
  - 10-event batches with 16 producers rose from 120–197 (old writer) to
    523–594 batches/s, and p95 fell from 129–167 ms to 37–53 ms.
  - 100-event batches with 16 producers rose from 62–68 (old writer) to
    80–96 batches/s, and p95 fell from 285–360 ms to 188–254 ms; this case is
    CPU bound at about 9.5k events/s.
  - Low-load single-request latency did not regress:
    `BenchmarkHTTPCommitLatency` p95 was 6.1–6.8 ms before and 5.4–5.9 ms
    after. "Before" ran from a `git archive HEAD` export.
- ADR 0009 has implementation notes. `ARCHITECTURE.md` §9.2 lists the new
  variables and §14.3 the defaults and the immediate-transaction mechanism.
- `make check`: exit 0.
- `make race-test`: exit 0 (all packages ok).
- `go test -race -count=10 -run 'PersistGroup|WriterWorker|DoImmediate|Ingestion|BatchWriter' ./internal/ingest ./internal/database`:
  ok. The same group tests with a btrfs `TMPDIR` (`-race -count=3`): ok.
- Durability smoke test (`TestDurableIngestionSubprocessSmoke`, `-count=3`):
  ok on tmpfs and ok with `TMPDIR=/var/tmp` (btrfs, same SSD). Under an
  in-repository `TMPDIR` it fails identically before and after this change:
  the control-socket path exceeds `sun_path` (h0-gate finding 1).
