### SFT-038 — Add bounded audit storage and migration `0004`

**Status:** Done
**Milestone:** 0.4.0
**Depends on:** SFT-037
**Issue/PR:** — (direct maintainer implementation)
**Completed:** 2026-07-28
**Completion evidence:** Added immutable migration
`0004_security_audit.sql`, advanced schema compatibility to 4, and introduced
the concrete `internal/audit` store. The `STRICT` schema constrains occurrence
time, category, normalized action, outcome, actor type, positive optional
historical entity IDs, a 128-byte request ID, and a 2 KiB JSON object; entity
IDs intentionally are not foreign keys so later source/Server deletion cannot
rewrite or block historical attribution. The store permits only 12
whitelisted nonsecret metadata fields, bounds each value to 256 UTF-8 bytes,
validates numeric/format/fingerprint/basename fields, rejects every control
character and unknown/sensitive key without echoing input, and exposes
`RecordTx` so successful privileged mutations and attribution can share a
coordinator transaction. Standalone recording, newest-first keyset pages,
category/outcome filtering, and age/count cleanup all remain bounded. Every
supported insert keeps the newest 100,000 rows; explicit cleanup deletes at
most 1,000 oldest `(occurred_at_us, id)` rows and application-event deletion
does not affect audit history. Fresh, schema-1, schema-2, and representative
schema-3 upgrades preserve Server, administrator, source, and event data,
reach schema 4, pass integrity, and prove older schema-3 compatibility refusal.
Migration rollback, database constraints, immutable trigger, equal-time
ordering, cursor edges, transaction rollback/commit, malformed stored
metadata, cap repair, independent retention, and eight-worker concurrent
recording are covered with real SQLite. Five-run 100,000-row benchmarks measure
1.301 ms median record-at-cap latency, 325.800 µs median newest-page latency,
and 23.935 ms median deliberate worst-case category scan; this evidence
justifies the single chronological index and defers speculative filter indexes.
`go fmt ./...`, `go vet ./...`, `go test -count=1 ./...`, `go test -race
-count=1 ./...`, focused audit/database race tests, and `git diff --check`
pass. Architecture, README, token-security, and the new
`docs/security/audit.md` document compatibility, bounds, resource cost,
privacy rules, and the explicit SFT-039 wiring boundary. The additive migration
adds no dependency, public route, background worker, telemetry, or external
service.

**Authoritative references:** `DOMAIN.md` §§22, 31; `ARCHITECTURE.md` §§10,
27; `PRODUCT.md` §19.4.

**Outcome:** Add immutable schema support and a concrete store for bounded,
sanitized administrator security and lifecycle audit records.

**Acceptance:**

- Migration `0004` preserves every supported prior-schema fixture and advances
  schema compatibility without editing earlier migrations.
- Audit records use explicit action/category/outcome/time/request fields and
  never store application payloads, passwords, tokens, session hashes, or
  authorization headers.
- Inserts requiring atomic attribution share the relevant coordinator
  transaction; retention is separate from application-log retention.
- Reads and cleanup are bounded and deterministically ordered.

**Verification:**

- Fresh and schema-1/2/3 migration tests assert preservation, integrity,
  schema-too-new refusal, rollback, ordering, and cleanup.
- Real-SQLite concurrency and sensitive-data tests run under the race detector.

**Impact:** Adds immutable migration `0004` and bounded audit disk use.
Operator/security documentation defines coverage and explicitly excludes
payload mirroring.

### SFT-039 — Audit privileged actions and add the audit view

**Status:** Done
**Milestone:** 0.4.0
**Depends on:** SFT-038
**Issue/PR:** — (direct maintainer implementation)
**Completed:** 2026-07-28
**Completion evidence:** Wired normalized security-audit attribution through
successful sign-in/session, administrator recovery, Server/token, source
alias/purge/removal, and retention mutations. Each successful privileged
mutation and its audit row share the same coordinator transaction; rejected
sign-ins use a separate bounded transaction, and audit failure cannot yield a
reported mutation success. Browser requests carry administrator and internal
request attribution, while focused maintenance commands use local-operator
attribution. Backup/restore/export/proxy-auth categories remain defined but
produce no placeholder events before those capabilities exist. Added one
recoverable, application-owned cleanup worker that runs at startup and hourly,
deleting at most 1,000 independently retained rows per pass. Added the
authenticated, no-store `/audit` workspace with required UTC ranges bounded to
366 days, exact category/action/outcome filters, 100-row newest-first keyset
pagination, escaped safe summaries, and a keyboard-focusable responsive table.
Real-SQLite tests cover successful/rejected sign-ins, actor attribution,
transaction rollback, concurrency, time/action filters, invalid bounds,
retention, worker lifecycle/error handling, immutability, and secret-free
escaped rendering. The 17-test Chromium suite passed in 49.5 seconds and covers
real multi-page data, filtering, hostile aliases, no-store, keyboard focus,
axe, dark/light themes, and 390px mobile layout. Documentation defines the
action taxonomy, future-action boundary, failure policy, lifecycle, query
bounds, and non-forensic limitation. `go fmt ./...`, `go vet ./...`, `go test
-count=1 ./...`, `go test -race -count=1 ./...`, `npm run frontend-check`,
`npm run playwright`, and `git diff --check` pass. Three one-second
100,000-row benchmark runs measured median record-at-cap latency of 1.300 ms,
newest-page latency of 349.295 µs, and deliberate oldest category scan latency
of 24.859 ms. No migration, dependency, outbound call, telemetry, or
additional runtime process was added.

**Authoritative references:** `DOMAIN.md` §22; `ARCHITECTURE.md` §§18, 27;
`DESIGN.md` §20.

**Outcome:** Record defined privileged actions and expose an authenticated,
sanitized, paginated audit view.

**Acceptance:**

- Login/session, administrator recovery, Server/token, source deletion,
  retention, backup/restore, export, and configuration actions record the
  specified safe outcome.
- Audit writes cannot turn a failed mutation into a reported success and
  atomic actions remain transactionally attributable.
- The UI supports bounded time/action/outcome inspection with no payload or
  credential fields.

**Verification:**

- Negative and real-SQLite tests cover success/failure recording, rollback,
  concurrency, actor/request attribution, retention, and secret-free output.
- Playwright covers filters, pagination, escaping, no-store, keyboard,
  accessibility, themes, and mobile behavior.

**Impact:** Adds audit writes to privileged paths and authenticated reads.
Storage/latency costs and failure policy are measured and documented.

### SFT-040 — Add bounded diagnostics and database checks

**Status:** Done
**Milestone:** 0.4.0
**Depends on:** SFT-039
**Issue/PR:** — (direct maintainer implementation)
**Completed:** 2026-07-28
**Completion evidence:** Added fixed-field production `database check`,
`database check --full`, and `diagnostics` commands without an arbitrary SQL
or support-data interface. Active quick checks use the bounded read pool and
order one passive WAL checkpoint through the maintenance coordinator; active
full checks are refused. Stopped quick/full checks open only an existing
regular database in SQLite read-only/query-only mode and never create,
migrate, checkpoint, or rewrite it. Reports validate a closed path-free set of
compatibility, schema/SQLite version, integrity, durability pragma,
writability-source, checkpoint/frame, file-byte, and page/free-page fields.
Corrupt, newer-schema, busy checkpoint, read-only, canceled, missing, and
active/stopped transitions return safe categorized failures. The Status page
now always shows schema and SQLite versions and offers an authenticated,
CSRF/origin-protected `Run safe database check` action with a concise
correlated result. The process-local diagnostic model now validates only
closed component/category pairs whose severity and summary are selected from
prewritten strings; optional request/recovery fields are bounded, the newest
100 entries overwrite the oldest, and audit/session/retention worker failures,
storage commits, queue saturation, and manual checks feed the same ring.
Authenticated Status and the active-only owner-socket diagnostics CLI expose
that bounded state with no paths, payloads, credentials, hashes, headers,
environment dump, or arbitrary errors. Real-SQLite tests cover healthy
quick/full checks, preservation, corruption, compatibility, permission-based
read-only state, cancellation, coordinator ordering, and a pinned-reader busy
checkpoint. CLI/handler tests cover active/offline routing, full-check refusal,
generic errors, request correlation, authentication, CSRF, bounded output, and
secret/path exclusion. The final full 17-test Chromium suite passed in 50.4 seconds,
including database-check notice/result, sanitized diagnostic rendering,
no-store, keyboard, dark/light axe checks, and 390px mobile behavior. `go fmt
./...`, `go vet ./...`, `go test -count=1 ./...`, `go test -race -count=1
./...`, `npm run frontend-check`, `npm run playwright`, and `git diff --check`
pass. On a 100,000-row migrated fixture, three one-second runs measured 19.068
ms median stopped quick-check latency and 39.515 ms median full-check latency,
with about 9.3 KiB and 157 allocations per invocation. Domain, architecture,
design, README, and `docs/operations/database-checks.md` document the safety,
privacy, lifecycle, stopped/active, and measurement boundaries. No migration,
dependency, telemetry, external call, persistent process-log storage, or
additional runtime process was added.

**Authoritative references:** `DOMAIN.md` §23; `ARCHITECTURE.md` §§10, 26–27,
30; `DESIGN.md` §18.

**Outcome:** Provide production CLI/UI database checks and a bounded,
sanitized diagnostic event stream without arbitrary SQL.

**Acceptance:**

- Checks report compatibility, integrity, WAL/checkpoint, writability, and
  relevant storage state with safe categorized failures.
- Active-safe checks are read-only or use approved bounded operations;
  stopped-server requirements are explicit.
- Diagnostics retain only a fixed number of sanitized operational events and
  exclude application content, secrets, hashes, paths requiring redaction, and
  environment dumps.
- No arbitrary query or support-data exfiltration interface is introduced.

**Verification:**

- Real-SQLite tests cover healthy, corrupt/incompatible fixture, busy,
  read-only, cancelled, and stopped/active operation.
- CLI/handler tests prove bounded output, generic errors, request correlation,
  authentication, and no sensitive logging.

**Impact:** Adds maintenance commands and sanitized operational state. No
telemetry, external calls, or unbounded internal process-log persistence.

### SFT-041 — Implement disk-full degraded mode and recovery

**Status:** Ready
**Milestone:** 0.4.0
**Depends on:** SFT-040
**Issue/PR:** —

**Authoritative references:** `DOMAIN.md` §§28–29; `ARCHITECTURE.md` §§10,
23–26; `PRODUCT.md` §19.4.

**Outcome:** Make storage-full behavior explicit: reject writes, preserve reads
where possible, report degradation, and recover without recreating data.

**Acceptance:**

- Ingestion maps full storage separately from temporary busy/I/O failures and
  never acknowledges an uncommitted batch.
- Read-only History/status/diagnostic paths remain available where SQLite
  permits; readiness reports the degraded state.
- Retention and operator recovery retry only bounded safe operations and never
  delete/recreate the database silently.
- Clearing the underlying condition returns the writer to service through a
  deterministic tested transition.

**Verification:**

- Filesystem/quota fault tests cover full database/WAL/temp paths, rollback,
  concurrent reads, retention interaction, restart, and recovery.
- Run lifecycle and ingestion race tests and confirm errors/logs contain no
  SQLite detail or payloads.

**Impact:** Operational failure behavior changes and must update recovery docs.
No migration; protects existing data over ingestion availability.

### SFT-044 — Implement stopped-server restore with rollback preservation

**Status:** Planned
**Milestone:** 0.4.0
**Depends on:** SFT-043
**Issue/PR:** —

**Authoritative references:** `DOMAIN.md` §26; `ARCHITECTURE.md` §§10, 25, 30;
`DESIGN.md` §21.

**Outcome:** Restore verified full or configuration-only backups only while the
server is stopped, preserving the current database as a recoverable rollback
copy.

**Acceptance:**

- Restore refuses an active server, incompatible schema, invalid artifact, or
  failed integrity check before replacing active state.
- The prior database and relevant WAL state are preserved as an explicitly
  named rollback copy; interruption never silently destroys both states.
- Restored sessions are absent/revoked and the next start requires fresh
  authentication.
- Post-restore migrations, integrity, critical queries, permissions, and
  startup behavior are verified before success.

**Verification:**

- Subprocess/fault tests cover both backup types, active-server refusal,
  interruption at replacement boundaries, schema mismatch, rollback recovery,
  and post-restore ingestion/history.
- Run migration fixture and audit/security tests with secret-free CLI output.

**Impact:** Destructive maintenance command with recoverable rollback and
explicit disk-space needs. No online restore or automatic down-migration.
