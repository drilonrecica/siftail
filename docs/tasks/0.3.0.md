### SFT-025 — Implement the bounded post-commit Live broker

**Status:** Done
**Milestone:** 0.3.0
**Depends on:** SFT-024
**Issue/PR:** — (direct maintainer implementation)
**Completed:** 2026-07-28
**Completion evidence:** The application lifecycle now owns one bounded Live
broker and drains the ingestion writer before stopping it. Committed batches
carry assigned event, source, and container-instance IDs and are sorted before
nonblocking publication. The broker caps command ingress at 256 commands and
the queued publication subset at 10,000 events/16 MiB; each of at most 16
subscribers has a 256-message/2 MiB ring. Subscriber or broker saturation closes
affected subscriptions with an explicit overflow outcome. Focused tests cover
ordering, exact filters, count/byte/connection limits, slow consumers,
publication loss, invalid filters, concurrent subscribe/publish/close, shutdown,
and publish-after-stop. Real HTTP/SQLite integration proves no pre-commit or
rolled-back publication. `go fmt ./...`, `go vet ./...`, `go test -count=1
./...`, `go test -race -count=1 ./...`, and `git diff --check` pass.

**Authoritative references:** `DOMAIN.md` §25; `ARCHITECTURE.md` §§14, 17;
`PRODUCT.md` §19.3.

**Outcome:** Add a lifecycle-owned broker that accepts only committed events
and fans them out without ever blocking the ingestion writer.

**Acceptance:**

- Subscribers receive newly committed events in assigned-ID order.
- Per-client delivery and broker command queues are bounded; slow clients are
  disconnected with an explicit overflow outcome.
- Publish remains nonblocking and never exposes uncommitted or rolled-back
  events.
- Shutdown closes subscriptions and owned goroutines deterministically.

**Verification:**

- Unit and race tests cover ordering, overflow, subscribe/unsubscribe races,
  slow consumers, shutdown, and publish-after-stop.
- Real ingestion integration proves commit-before-publication and no
  publication on rollback.

**Impact:** No migration or public route. Adds bounded resident memory and
concurrency owned by the application lifecycle; payloads remain absent from
process logs.

### SFT-030 — Add source aliases, clear-logs, and remove-source workflows

**Status:** Done
**Milestone:** 0.3.0
**Depends on:** SFT-029
**Issue/PR:** — (direct maintainer implementation)
**Completed:** 2026-07-28
**Completion evidence:** Added coordinator-serialized alias, Clear logs, and
Remove source operations plus protected source-detail forms. Alias input is
trimmed, bounded to 128 UTF-8 bytes, and changes only `sources.alias`; tests
prove stable keys and event ownership are unchanged. Both destructive
operations capture a source event-ID watermark and delete at most 10,000 events
per transaction. Clear logs retains the source, alias, Server, and container
observations. Remove source deletes aliases and unreferenced containers, removes
source metadata only when referentially safe, never removes the trusted Server,
and preserves events committed after the watermark. A real coordinator
interleaving test commits such an event between purge transactions and proves
the source remains safely rediscoverable. Successful operations publish
non-blocking source-purged/source-removed controls after database completion.
All POST routes use the existing authenticated, exact-Origin, bounded form, and
CSRF middleware; handlers additionally reject unknown/duplicate fields. Clear
logs requires the exact display name, while Remove source requires the stronger
`remove <display name>` phrase. Copy distinguishes Clear view, Clear logs, and
source removal and makes no forensic-erasure claim. Real-SQLite tests cover
10,002-event chunking, rollback, source/Server ownership, alias removal,
cancellation, missing sources, coordinator interleaving, and cascades; handler
tests cover protection, confirmations, validation, escaping, and controls.
Targeted mutation tests pass ten ordinary repetitions and the interleaving test
passes ten race repetitions. The production-binary browser workflow covers
hostile aliases, confirmation copy and focus, session expiry before mutation,
Clear logs preservation, and removal. `go fmt ./...`, `go vet ./...`, `go test
-count=1 ./...`, `go test -race -count=1 ./...`, JavaScript/frontend checks, 12
Chromium scenarios in 37.2 seconds, and `git diff --check` pass. No migration or
dependency was added; persisted audit events remain explicitly assigned to the
later `0.4.0` audit task.

**Authoritative references:** `DOMAIN.md` §§13, 17, 30–31; `DESIGN.md` §15;
`ARCHITECTURE.md` §§15, 18.

**Outcome:** Add safe source presentation and lifecycle mutations without
changing source identity or confusing browser-only clearing with deletion.

**Acceptance:**

- Alias changes affect presentation only and do not rewrite event ownership or
  source identity.
- Clear view remains browser-local; Clear logs deletes retained application
  events only after explicit confirmation.
- Remove source follows the documented ownership cascade and emits the required
  client control event without waiting for clients.
- All mutations require authentication, CSRF, exact Origin, and coordinator
  serialization.

**Verification:**

- Real-SQLite transaction tests cover rollback, ownership boundaries,
  concurrent ingestion, aliases, purge, and deletion.
- Playwright covers confirmations, copy, focus, session expiry, escaping, and
  destructive-action distinctions.

**Impact:** Destructive actions are explicit and audited once audit storage
arrives in `0.4.0`; no claim of forensic erasure. Migration need is determined
from the existing schema before implementation.

### SFT-033 — Implement bounded age and database-size retention

**Status:** Planned
**Milestone:** 0.3.0
**Depends on:** SFT-032
**Issue/PR:** —

**Authoritative references:** `DOMAIN.md` §§16–17; `ARCHITECTURE.md` §§10, 23;
ADR 0002.

**Outcome:** Add lifecycle-owned retention that deletes the canonical oldest
events in bounded writer-coordinated transactions.

**Acceptance:**

- Retention enforces global age and database-size limits, deleting by
  `min(event_at_us, received_at_us), id` in bounded chunks.
- It never deletes authentication, configuration, session, or audit records
  and never runs routine full `VACUUM`.
- Ingestion remains bounded and reads remain available while retention works;
  cancellation and shutdown leave a valid database.
- Purges produce client control events only after commit.

**Verification:**

- Real-SQLite and race tests cover age/size triggers, equal timestamps,
  concurrent ingestion/reads, rollback, cancellation, restart, and shutdown.
- Benchmarks record chunk latency, writer interference, WAL/database behavior,
  and resource impact at representative sizes.

**Impact:** Permanently deletes retained application events according to
administrator policy. Operational docs must explain sizing, recovery limits,
and filesystem-dependent space reclamation.
